# Design

把已经明确的需求设计成可由实现者直接执行、可由审查者独立判断的工作。保持具体，但不要提前实现。

## 执行

1. 阅读适用规则、需求来源、仓库结构、相关实现和测试，记录设计基线。不要依赖聊天中未提供或未作为 Artifact 传入的前置 Skill 私有状态。
2. 检查需求是否足以设计：
   - 充分时直接继续，不要求先运行 Spec。
   - 缺口可由仓库回答时先调查。
   - 只有少量设计阻塞项时，一次询问一个，并给出推荐答案和取舍。
   - 产品目标、范围或验收仍根本不清楚时停止并请求补充；可以建议使用 Spec，但不要自动调用它。
3. 评估范围。多个可独立交付的子系统应拆为独立设计或明确阶段，不要塞进一个不可审查的大任务。
4. 选择符合仓库现有模式的最小完整方案。只在公共契约、成本、兼容性或风险存在实质差异时比较备选方案，并明确推荐结论。
5. 定义组件职责、接口、数据与状态流、错误处理、迁移和验证方式。精确到实现者无需重新做关键设计，但避免复制大段实现代码。
6. 拆成带依赖的任务。每个任务都要产生可独立审查和验证的结果；把脚手架、配置和文档并入真正需要它们的任务。
7. 生成设计文档并自检需求覆盖、占位符、命名和类型一致性、循环依赖、兼容遗漏与不可执行步骤。
8. 报告文档路径、关键决定和残余风险，然后停止。不要自动调用 Implement、修改业务代码或创建 Noctis Run。

## 文档

默认写入 `docs/designs/<topic>.md`；优先使用用户指定路径或仓库既有约定。按复杂度缩放内容，只保留适用章节：

- 需求来源、目标与设计基线
- 约束、推荐方案与必要的备选取舍
- 组件边界、职责和涉及的文件或模块
- 接口、数据结构、状态转换与数据流
- 失败路径、兼容性、迁移、回滚、安全和可观测性
- 任务 DAG
- 需求、任务与验证的覆盖矩阵
- 风险、明确假设与非阻塞待办

任务使用稳定 ID，如 `TASK-001`，并至少包含目标、依赖、涉及文件或模块、输入与输出接口、变更内容、对应需求、验收条件和验证命令或方法。不要使用 `TBD`、`TODO`、“适当处理错误”或“补充相关测试”等占位表达。

独立调用时可以按用户请求写设计文档；未经明确要求不要提交、推送、修改业务代码或外部系统。

## Ars 调用

收到 `ars.task/v1` 时：

- 只接受 provider `design`、capability `solution.design` 的 Task。输入可以是 `requirements.spec` Artifact、其他需求文档或完整的 Task instructions，也可以在需求明确时没有前置 Artifact。
- 以 Task 的 instructions、inputs、acceptance、workspace 和 effects 为完整边界。必要信息不足时返回 `input-required`，不要把 Spec 设为安装或执行前置条件。
- 完成时返回 `ars.result/v1`，其中 `solution.design` Artifact 的媒体类型为 `text/markdown`。Task 允许内联交付且没有 workspace 写入授权时使用 inline locator；Task 要求落盘但缺少授权时返回 `blocked`。
- 写入 workspace 时只使用精确相对路径，并遵循 envelope 对 `workspace.write`、`git.commit` 和 Git Artifact 的共同要求。

解析 Task 或构造 Result 前读取 [references/ars-envelope.md](references/ars-envelope.md)，严格复制关联字段并只返回契约允许的字段。

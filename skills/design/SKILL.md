# Design

把明确需求转换为足以指导实现的技术方向，同时给实现者保留局部判断空间。

## 工作方式

- 从仓库结构、现有模式、依赖、需求和约束建立设计基线。
- 选择最小完整方案，说明相关模块职责、interface、数据与状态流、失败路径，以及真正重要的兼容或迁移决策。
- 优先设计深模块：让较多行为位于较小 interface 后，并把可变依赖放在有真实替代实现的 seam 上。
- 只在存在实质取舍时比较备选方案，明确推荐、理由和被放弃方案的代价。
- 验证设计是否能通过公开 interface 测试，并说明关键风险如何取得证据。

## 边界

- 不重新定义产品目标；缺失业务决定会改变设计时请求输入。
- 不把设计扩张为逐文件施工手册，也不为显而易见的局部实现制造抽象。
- 不创建任务图、运行状态或执行分工，也不调用实现或其他 Skill。
- 简单变更只交付关键取舍；复杂、跨模块或需要持久评审的方案才写正式设计文档。

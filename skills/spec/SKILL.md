# Spec

用最少必要沟通把用户意图固化为需求事实。只追问会改变范围、可观察行为、约束或验收结论的问题；不要把访谈本身当成交付。

## 执行

1. 阅读适用规则、用户提供的材料，以及与需求直接相关的现有文档和代码。优先从仓库查明事实，不把可调查的问题抛给用户。
2. 判断当前信息是否足够：
   - 足够时直接综合，不重复询问已经明确的内容。
   - 存在可由仓库回答的缺口时先调查，再记录证据或假设。
   - 存在会改变结果的用户选择时，一次只问一个最高优先级问题，同时给出推荐答案、理由和主要取舍，然后等待回答。
3. 按依赖顺序解决问题。一个答案使后续问题失效时立即删去这些问题；不要预先发送问题清单。
4. 阻塞性选择全部解决后，汇总一次关键决定并确认。用户已要求不中断地完成，或输入本身已获得批准时，省略这次确认。
5. 生成需求文档并自检。修正矛盾、重复、含糊措辞、不可观察的验收条件和无主的阻塞问题。
6. 报告文档路径、关键假设和仍需后续处理的非阻塞事项，然后停止。不要自动调用 Design、Implement 或创建 Noctis Run。

## 文档

默认写入 `docs/specs/<topic>.md`；优先使用用户指定路径或仓库既有约定。按复杂度缩放内容，只保留适用章节：

- 问题与背景
- 目标和成功指标
- 用户、角色与关键场景
- 范围与非目标
- 编号需求，如 `REQ-001`
- 业务规则、领域术语与用户指定约束
- 兼容性、安全、隐私或数据要求
- 编号验收条件，如 `AC-001`
- 已确认决定、明确假设与非阻塞待办

用用户可观察的结果描述需求和验收。可以记录用户明确要求的技术约束，但不要选择架构、列出实现文件、编写代码或拆分实现任务。阻塞性未决问题尚未解决时不要把文档描述为完成。

独立调用时可以按用户请求写文档；未经明确要求不要提交、推送或修改外部系统。

## Ars 调用

收到 `ars.task/v1` 时：

- 只接受 provider `spec`、capability `requirements.spec` 的 Task。输入可以为空，也可以包含用户材料或前置 Task 的 Artifact。
- 以 Task 的 instructions、inputs、acceptance、workspace 和 effects 为完整边界。需要用户决定时返回 `input-required`，不要自行补写业务事实。
- 完成时返回 `ars.result/v1`，其中 `requirements.spec` Artifact 的媒体类型为 `text/markdown`。Task 允许内联交付且没有 workspace 写入授权时使用 inline locator；Task 要求落盘但缺少授权时返回 `blocked`。
- 写入 workspace 时只使用精确相对路径，并遵循 envelope 对 `workspace.write`、`git.commit` 和 Git Artifact 的共同要求。

解析 Task 或构造 Result 前读取 [references/ars-envelope.md](references/ars-envelope.md)，严格复制关联字段并只返回契约允许的字段。

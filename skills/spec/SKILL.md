# Spec

把用户意图整理成实现者和验收者可以共同判断的需求事实。内容规模和形式跟随任务与仓库惯例，不套固定模板。

## 工作方式

- 从用户材料、现有文档和代码中确认事实，保留用户使用的领域语言。
- 只追问会改变目标、范围、业务规则、兼容性或验收结论的选择；能从工作区可靠确认的信息不要反问。
- 说明目标、非目标、约束、关键场景和可观察的验收条件。
- 区分已确认决定、合理假设和仍需用户决定的事项。
- 验收条件描述用户或外部系统能观察到的结果，并覆盖关键失败与边界场景。

## 边界

- 描述“需要什么”，不要提前锁定架构、文件或实现步骤。
- 不用技术细节填补缺失的业务决定；关键信息不足时明确请求输入。
- 只有请求明确需要可复用文档时才写文件，并优先使用仓库已有文档位置和格式。
- 直接交付规格，不调用设计、实现或其他 Skill。
